# 개발 순서

## 1. 개인 AI에서 공공자료 조회

현재 구현: 두 원천의 예시 목록, 원문 URI 조회, 도서관 자료에서 작성자 관계 따라가기, 실행 기록 다운로드, 같은 코드를 사용하는 stdio MCP.

다음 범위는 찾을 자료를 정하지 못한 사람도 사용할 수 있는 검색 경험이다. 먼저 질문 10개와 기대 근거를 사람이 확정하고, 기관의 실제 검색 성능을 확인한다. 현재 예시 목록을 자유어 검색으로 설명하지 않는다. 공식 MCP가 이미 답하는 질문은 다시 구현할 필요가 있는지 먼저 비교한다.

기관 간 연결은 공통 식별자 또는 검증 가능한 대응표가 있는 사례에서만 추가한다. 이름이 비슷하다는 이유만으로 두 대상을 같은 것으로 합치지 않는다.

## 2. 팀 Wiki

팀 Wiki는 다음 개발 대상으로 유지한다. 별도 앱으로 진행하며 이번 LOD 조회기에 조직용 권한 기능이 있다고 설명하지 않는다.

첫 사용 장면은 같은 자료를 볼 수 있는 작은 팀이 Google Drive 폴더 하나를 Wiki로 유지하는 것이다. 파일의 추가, 수정, 이동, 삭제와 접근 철회를 처리하고, 원문 버전과 Wiki 문장을 연결한다. 기존 근거 검토 모듈은 원문 변경 후 문장을 재검토하는 단계에서 연결한다.

WeKnora를 우선 검토하되 현재 원본의 커넥터와 라이선스를 구현 직전에 다시 확인한다. Obsidian은 로컬 폴더, OneDrive는 별도 공급자 연결로 확장한다. 단순한 파일 동기화와 사용자별 원천 권한 상속을 구분한다. 실제 팀 문서 연결 전에는 공개 또는 합성 문서로 삭제와 접근 철회 시험을 먼저 한다.

## 3. 연구 준비

제품 개발 기록을 남기면서 비교 과제를 준비한다. 검색 품질이나 Wiki 유지 비용이 개선됐다는 주장은 실제 비교 결과가 나온 뒤에 한다. 논문 때문에 사용 목적을 바꾸지 않는다.
